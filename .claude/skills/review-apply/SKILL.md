# レビュー結果の検討と反映

`uv run review <file.md> -m MODEL` は結果を `<stem>.txt`（例: `clif/04-weyl-algebra.md` → `clif/04-weyl-algebra.txt`）に書き出す。このスキルは、その指摘を精査して対応方針を提示し、**ユーザーの最終判断を得てから**記事を修正する手順。

レビュー全体の運用手順は [REVIEW.md](../../../REVIEW.md) を参照。

## 原則

- **即座に修正しない。** 指摘の妥当性を自分で検討し、見解を添えて判断を求める。承認された項目だけを修正する。
- **LLMの指摘には誤りが混じる。** 「レビューが指摘したから」は修正の理由にならない。数式は検算し、記事側が正しい場合は根拠を添えて見送りを提案する。
- **参照記事への修正提案も同じ扱い。** レビュープロンプトは参照記事側の修正提案も許しているため、指摘が対象記事ではなく参照記事に向いていることがある。勝手に他の記事を触らず、対象記事とは分けて提示し、個別に判断を求める。

## 手順

### 1. レビュー結果と記事を読む

```bash
cat <stem>.txt
```

対象記事と、`<stem>-prompt.md` があれば front matter の参照記事も読み、指摘が前提としている文脈を確認する。

### 2. 各指摘を検討する

指摘ごとに次を判定する。

- **事実確認** — 指摘が記事の記述を正しく読めているか。レビューが誤読している指摘は少なくない。
- **数式の検算** — 係数・符号・添字・極限の取り方に関わる指摘は必ず確認する。手計算で足りなければ検証スクリプトを書く。スクリプトは対象ディレクトリの `check/` に置き、`uv run` で実行する（一時的な確認ならスクラッチパッドでよい）。
- **プロジェクト方針との整合** — 指摘に従うと方針を崩す場合がある。方針が優先する。
    - 本文はですます調、`&&&prf` 内はである調（意図的な使い分け）
    - 次回予告を書かない。後続記事の内容を約束する書き方（「次回は〜を導きます」）は `[[slug]]` もプレーンテキストも、末尾でも冒頭でも置かない。伏線は回収する側の記事に後方参照として書く。例外は、扱いきれない話題を「本記事では扱わない」と断って先送りする場合のみ
    - 日本語で `——`（em dash）を使わない
    - `&&&` の type は内容の性質に応じて使い分ける（`&&&rem` に丸めない）
    - 記法の約束（`≅` と `=` の使い分けなど）
- **影響範囲** — 修正が他の記事の記述と食い違わないか。特に、対象記事が公開済みの場合は Mathlog への反映作業が発生する（[REVIEW.md](../../../REVIEW.md) の「公開済み記事の修正手順」）。

判定は次の3分類にまとめる。

| 区分 | 意味 |
|---|---|
| 対応 | 指摘は妥当。修正内容を具体的に示す |
| 要判断 | 妥当だが、方針・構成・分量とのトレードオフがある。選択肢を示す |
| 見送り | 指摘が誤り、または記事側の判断が優先する。根拠を示す |

### 3. 方針を提示して判断を求める

表かリストで一覧し、各項目に**区分・指摘の要約・自分の見解（と根拠）・修正するならどう直すか**を書く。

- 「レビューがこう言っている」で終わらせず、**自分の判断を明示する**。
- 誤指摘は誤指摘と書く。指摘を全部飲む前提で並べない。
- 修正案は、実際に置き換える文面（差分のイメージ）まで具体化する。長い場合は該当箇所の行番号と要点でよい。
- 参照記事への修正提案は**別の節**に分け、どのファイルのどこをどう直すかと、その記事が公開済みかどうか（`uv run reftools show <path>` で URL の有無を確認）を添える。

そのうえで、どれを反映するかユーザーに確認する。`AskUserQuestion` を使うか、番号付きで列挙して回答を待つ。

### 4. 承認された項目を修正する

- 承認された項目だけを修正する。ついでの改善を混ぜない。
- 参照記事の修正は、対象記事とは別に承認を得てから行う。
- 数式やラベルを触った場合は、修正後に確認する。
    ```bash
    uv run reftools show <path>   # [[slug]]参照の健全性
    uv run reftools check         # slug全体の整合性（slugを変更した場合）
    ```
- `<stem>.txt` は削除しない。`uv run articles pending` のレビュー済み判定に使われる。
- 公開済み記事を修正した場合は、Mathlog への反映が必要であることを最後に伝える（反映作業自体はブラウザ操作なのでユーザーが行う）。

### 5. 結果を報告する

- 修正した項目、見送った項目、ユーザーの判断で保留になった項目を区別して報告する。
- 検算した内容があれば、何をどう確認したかを1行で添える。
