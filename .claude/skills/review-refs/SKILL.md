# レビュー参照記事の選定

`uv run review <file.md> -m MODEL` が自動で読み込む `<stem>-prompt.md` を用意する手順。参照記事をリポジトリ全体から選んで front matter に書き、記事固有の重点項目があれば本文に書く。

レビュー全体の運用手順は [REVIEW.md](../../../REVIEW.md)、ツールの仕様は [src/review/README.md](../../../src/review/README.md) にある。参照記事は「用語・記法・構成上の位置づけを確認するための文脈」としてコンテキストに含まれる。したがって選定の目的は**整合性の食い違いを検出できる記事を選ぶこと**であり、単に話題が近い記事を並べることではない。

## 手順

### 1. 対象記事を読む

冒頭の導入と「まとめ」を中心に、次を把握する。

- 「前回」「前記事」として無証明で持ち込んでいる前提（定義・記号・定理）
- 本文で定義し直している基本概念（他記事に定義の本体がある可能性が高い）
- 本文中の `[[7shi-*]]` 自己引用

### 2. 除外リストを取得する

```bash
uv run articles pending
```

**未公開（Mathlog未掲載）または未レビュー（対になる `.txt` がない）の記事は参照記事に選ばない。** 内容が確定しておらず、整合性の基準にならないため。対象記事自身がこのリストに載っているのは正常（レビュー前なので当然）。

なお、このコマンドが出すのは「未公開**かつ**未レビュー」の記事である。公開済みだが `.txt` がない古い記事は出力されないが、内容は公開によって確定しているので参照に選んでよい。逆に、未公開でもレビュー済み（`.txt` がある）の記事は内容が固まっているので選んでよい。判断に迷ったら `articles.tsv`（URLの有無＝公開状況）と `<stem>.txt` の有無を直接確認する。

#### 除外対象が最大の前提供給元だった場合

除外リストの記事が、対象記事にとって手順4の優先度1（前提を供給する記事）に当たる場合は、**黙って外さずユーザーに判断を求める。** その記事を欠いたレビューは、最も食い違いやすい対を検査できないまま終わるため、選定の失敗に近い。次の選択肢を提示する。

1. **先にその記事をレビューする** — 対象記事を後回しにし、前提側の記事に対してこのスキルを適用し直す。前提が確定してから対象記事をレビューできるので、手戻りが最も少ない。原則としてこれを推奨する。
2. **未レビューのまま参照に含める** — 内容が動く可能性を承知のうえで `refs` に入れる。前提側の記事の公開予定が先送りされている場合など。
3. **外したまま進める** — 食い違いうる点を本文の重点項目として文章で書き、参照記事の全文は渡さない。

提示するときは、その記事が何を供給しているか（記号・定義・定理）と、欠いた場合に検査できなくなる点を具体的に書く。ユーザーが選ぶまで `<stem>-prompt.md` は確定させない。

### 3. 候補を集める

複数の経路で機械的に洗い出す。1つの経路だけに頼らない。

```bash
# 自己引用の引用先を逆引き（[[7shi-xxx]] → ファイルパス）
uv run reftools show <target.md>      # 記事が引いている slug 一覧
cat slugs.tsv                          # md ↔ slug の対応表

# 対象記事を引用している記事（後方参照）
grep -rl "\[\[7shi-<対象のslug>\]\]" --include=*.md .

# 同ディレクトリの連番（直前・直後）
ls <dir>/

# 主要概念のキーワード横断検索（シリーズをまたぐ重複を拾う）
grep -rln "<概念語1>\|<概念語2>" --include=*.md .
```

シリーズをまたぐ接続は見落としやすいので、キーワード検索は必ず行う（例: 一般化パウリ行列 ↔ hopf の qudit パウリ群、交換子 ↔ lie の随伴作用）。

### 4. 優先順位をつけて2つに絞る

**原則として2つ。** `review` 側は件数を制限していないので、適切な数に絞るのはこの手順の責任。参照記事は全文がコンテキストに入るため、増やすほどトークン消費が膨らみ、レビューの焦点もぼやける。3つ目以降は、明確な整合性リスクを説明できる場合に限る。

優先度の高い順:

1. **前提を供給する記事** — 対象記事が定義なしに使う記号・定理の出所。記法の食い違いはこの対でしか検出できないため、ほぼ必ず1つ目に入る。多くは同シリーズの直前記事。
2. **同じ概念の定義本体を持つ記事** — 対象記事が本文で定義し直している概念（交換子、テンソル積など）を、別シリーズで正面から扱っている記事。定義の重複・矛盾や、引用先 slug が適切かを判定できる。
3. **同じ構造を別の文脈で扱う記事** — 呼称や強調点の食い違いを検出できる。

避けるもの:

- 未公開/未レビューの記事（手順2で除外。ただしそれが優先度1に当たる場合は手順2の判断を経る）
- 話題は近いが対象記事側が自己完結していて食い違う余地のない記事
- 極端に長い記事（`wc -c` で確認。70KB超は、整合性リスクが明確でなければ次点に回す）

### 5. プロンプトファイルを生成する

選定結果は `<stem>-prompt.md` に書き出す。この名前で対象記事と同じディレクトリに置くと `review` が自動で拾い、YAML front matter の `refs` が参照記事として読み込まれる。`-p` も `-r` も指定不要になる（[src/review/README.md](../../../src/review/README.md)）。

```
clif/04-weyl-algebra.md  →  clif/04-weyl-algebra-prompt.md
```

- ファイル名は対象ファイル名の `.md` を `-prompt.md` に置き換えたもの（stem を省略しない）。この命名でないと自動認識されない。
- レビュー結果は `<stem>.txt` に出力されるので衝突せず、`articles pending` の未レビュー判定（`<stem>.txt` の有無）にも影響しない。
- front matter の `refs` は**リポジトリルートからの相対パス**で書く（`uv run articles pending` の出力と同じ形式）。

```markdown
---
refs:
  - clif/03-gpm-gca.md
  - lie/05-bch-adjoint.md
---

添付は「クリフォード代数」シリーズ第4回の記事です。（以下、レビュー観点）
```

手順1〜3で、汎用プロンプト（数式の正しさ・分かりやすさ・用語や記法の一貫性・日本語表現）だけでは拾えない**この記事固有の重点項目や注意点**が見つかった場合は、front matter に続けて本文にレビュー観点を書く。見つからなければ front matter だけのファイルにする（本文が空なら汎用プロンプトが使われる）。

書く重点項目の例:

- 参照記事との間で食い違いうる具体的な点（記号の定義、添字規約、用語の揺れ、定義の重複）
- 記事固有の構成上の制約（不要な前方参照が残っていないか、シリーズ内での位置づけ）
    - **次回予告は書かない方針。** 後続記事の内容を約束する書き方（「次回は〜を導きます」）は、末尾でも冒頭の導入でも置かない。伏線は張る側ではなく、回収する側の記事に後方参照として書く。前方参照が許されるのは、扱いきれない話題を「本記事では扱わない」と断って先送りする場合だけ。
- その記事で特に検算してほしい導出（成分計算、極限の取り方、係数や符号）
- プロジェクト方針のうちこの記事で崩れやすいもの（`&&&` の type の使い分け、本文はですます調・`&&&prf` 内はである調、`——` を使わない、砕けた比喩を避ける）

本文の書き方:

`-p` の本文はデフォルトプロンプト [src/review/PROMPT.txt](../../../src/review/PROMPT.txt) を**置き換える**。したがって、デフォルトを土台にして重点項目を足したものとして書く。デフォルトは次の構成になっている。

```
添付は数式を含む日本語の技術記事です。以下の観点でレビューしてください。

- 数式・数学的主張の正しさ
- 説明の分かりやすさ、論理の飛躍の有無
- 用語・記法の一貫性
- 日本語表現の自然さ

指摘事項を箇条書きで挙げてください。問題がなければその旨を書いてください。
```

- 冒頭の1文は、記事の位置づけ（シリーズ名、前後関係、前提とする知識）を補って具体化する。
- 4つの観点は落とさない。重点項目は、この4観点に対象記事固有の内容を書き足すか、独立した項目として追加する。「用語・記法の一貫性」に参照記事との照合点を書き足す形が使いやすい。
- 末尾の1文はそのまま残す。
- 全体で10項目程度までに収める。デフォルトの4観点が埋もれるほど項目を増やさない。
- ボックス記法と `[[label]]` の説明は `COMMON.txt` が自動で渡すため、書かない。
- 対象ディレクトリに `PROMPT.txt`（例: [lebesgue/PROMPT.txt](../../../lebesgue/PROMPT.txt)）がある場合、そこにはシリーズ全体の編集方針が書かれている。丸ごとコピーするのではなく、対象記事に効く項目だけを拾って取り込む。

### 6. 提示する

- 各参照記事について、**何が食い違いうるか**を具体的に書く（「関連が深い」だけでは選定理由にならない）
- 本文に重点項目を書いた場合は、何を重点にしたかを数行で説明する
- そのまま実行できるコマンド行を添える（`<stem>-prompt.md` は自動認識されるので `-p` も `-r` も不要）
- 次点候補があれば1つ、外した理由（長さ・リスクの低さ）とともに1行で添える

```bash
uv run review <target.md> -m <model>
```

選定とプロンプト生成までがこのスキルの範囲。**`uv run review` は実行しない。** APIキーとトークン消費が絡むため、コマンドを提示してユーザーの実行に委ねる（モデル名もユーザーが決めるので、指定がなければ `<model>` のままにする）。
