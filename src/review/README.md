# review

Markdown記事をLLMにレビューさせ、結果を同名の`.txt`ファイルに保存するツールです。

```bash
uv run review <file.md> -m MODEL [-p PROMPT.md] [-r REF.md]...
```

| 引数 | 説明 | デフォルト |
|---|---|---|
| `file` | レビュー対象の`.md`ファイル | 必須 |
| `-m`, `--model` | ベンダープレフィックス付きのモデル名（例: `openai:gpt-4.1-mini`） | 必須 |
| `-p`, `--prompt` | レビュー観点を記述したプロンプトファイル（`.md`/`.txt`） | `<stem>-prompt.md`があればそれ、なければ組み込みの汎用プロンプト |
| `-r`, `--ref` | 参照用の`.md`ファイル（複数指定可） | なし |

`-r`で指定したファイルはレビュー対象ではなく、用語・記法・構成上の位置づけを確認するための参照文脈としてコンテキストに含まれます。他の記事との一貫性を確認したい場合に使います。

記事とレビュー観点のプロンプトの間には、`-p`の有無によらず[COMMON.txt](COMMON.txt)の内容が渡されます。これはMathlogのボックス記法（`&&&type title`〜`&&&`）とラベル参照（`[[label]]`）の説明で、LLMがこれらをMarkdownの誤りと誤認するのを防ぎつつ、typeの使い分けの妥当性をレビュー観点に含めるためのものです。

`-p`を省略した場合、レビュー対象と対になる`<stem>-prompt.md`（例: `clif/04-weyl-algebra.md`に対する`clif/04-weyl-algebra-prompt.md`）が同じディレクトリにあれば、それを自動的に使います。記事ごとのレビュー観点と参照記事を用意しておけば、`-p`も`-r`も指定せずに実行できます。

対になるファイルもない場合は、[PROMPT.txt](PROMPT.txt)の汎用プロンプト（数式の正しさ・分かりやすさ・用語や記法の一貫性・日本語表現を確認）を使います。ディレクトリごとの編集方針（構成上の位置づけ、記法の使い分けなど）を踏まえたレビューをさせたい場合は、そのディレクトリに`PROMPT.txt`のようなプロンプトファイルを用意し`-p`で指定します（例: [lebesgue/PROMPT.txt](../../lebesgue/PROMPT.txt)）。

## front matterによる参照記事の指定

プロンプトファイルの冒頭にYAML front matterを置くと、`refs`に並べたファイルが`-r`と同じ参照記事として読み込まれます。記事ごとに参照記事が決まっている場合、コマンドラインから`-r`を繰り返す手間がなくなります。

```markdown
---
refs:
  - clif/03-gpm-gca.md
  - lie/05-bch-adjoint.md
---

添付は「クリフォード代数」シリーズの記事です。以下の観点でレビューしてください。

（以下、レビュー観点）
```

- パスは**リポジトリルートからの相対**で書きます（`uv run articles pending`の出力をそのまま使えます）。
- パースにはPyYAMLを使っているので、`refs: [a.md, b.md]`のインライン形式など通常のYAMLの書き方がそのまま使えます。`refs`以外のキーは無視されます。
- `-r`を併用した場合は、front matterの分に続けて追加されます（重複は除去）。
- `<stem>-prompt.md`という名前にしておけば`-p`の指定も省略できます（前節参照）。
- 件数に制限は設けていません。ただし参照記事は全文がコンテキストに入るため、トークン消費が増えるだけでなくレビューの焦点もぼやけます。2件程度に絞るのが目安です。
- front matterだけで本文が空の場合は、汎用プロンプトが使われます。参照記事の指定だけをファイル化したい場合に使えます。
- 実行時に読み込んだ参照記事のパスが標準出力に表示されます。

結果は指定したファイルと同じ場所に`<stem>.txt`として保存されます。

実行の最後にはトークン使用量をリポジトリ直下の`usage.jsonl`に追記します（詳細は[usage/README.md](../usage/README.md)参照）。
